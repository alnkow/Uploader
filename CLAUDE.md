# CLAUDE.md

## Проект

Фронтенд загрузки данных на внешний сервер: фото, видео, MBTiles, архивы zip и rar (в том числе многотомные); точный список расширений — в спецификации (§5.7). Пользователь выбирает тип данных, заполняет атрибуты, выбирает файлы и отправляет их пакетом; пакеты загружаются по очереди. После загрузки сервер копирует данные во внутренние контуры и удаляет исходные данные; пользователь о контурах не знает, и в интерфейсе они не упоминаются. Загрузка должна возобновляться после потери соединения.

**Статус (13.10.2026):** есть каркас в `src/upload/`: менеджер загрузок и компоненты с минимальными стилями. Код рассчитан на перенос в основное приложение. `package.json`, `dev/` и `vite.config.ts` нужны только для локальной проверки с заглушкой бэкенда и в приложение не переносятся.

**Сейчас делаем только минимальную рабочую версию** (D19 в спецификации): загрузка с докачкой, очередь, прогресс, «Повторить» и «Отменить». Всё, что не нужно для неё, не добавлять, даже мелочи для удобства; список отложенного — в D19.

**Зона ответственности — только фронтенд.** Бэкенд, nginx и сеть делают другие люди. Не предлагай задач по ним; если от них что-то нужно, сформулируй это как требование или вопрос для передачи (§6 спецификации).

**Источник истины — `UPPY_UPLOAD_IMPLEMENTATION.md`:** требования, принятые решения (§2), открытые вопросы (§3), контракт API, план и матрица тестов. Прежде чем менять архитектуру, прочитай его.

**`UPLOAD_MANAGER_EXPLAINED.md`** — объяснение устройства загрузки простым языком для новичков; **`UPLOAD_MANAGER_EXPLAINED.html`** — та же тема самодостаточной страницей со схемами и песочницей очереди (без внешних зависимостей, её пересылают коллегам). Меняешь поведение `UploadManager` или компонентов — обнови оба.

**`UPLOAD_API_FLOW.html`** — все запросы загрузки по шагам (адреса, заголовки, тела, ответы, куда фронт кладёт данные) для бэкендера, опубликован: https://claude.ai/artifact/Vo3zDepZLyJPGpwv3Pzbfo (обновлять публикацией того же файла). Меняешь контракт API (§4.3) или обработку ответов — обнови его.

## Стек

- React + TypeScript, react-hook-form.
- Uppy 6.x: `@uppy/core`, `@uppy/react`, `@uppy/tus`. Не используем `@uppy/golden-retriever`, `@uppy/dashboard`, `@uppy/aws-s3`.
- В Uppy 6 нет пакетов `@uppy/utils`, `@uppy/store-default`, `@uppy/companion-client`: импорт из `@uppy/core/utils` и аналогичных подпутей.
- Бэкенд: Tus-сервер с файловым хранилищем за nginx (тот же origin, CORS не нужен). Tus-запросы авторизуются upload-токеном пакета, остальной API — access-токеном пользователя.

## Команды

Для людей то же самое расписано в `README.md` — меняешь команды, порты или настройки заглушки, обнови и его.

- `npm install` — один раз.
- `npm run mock` — заглушка бэкенда (`dev/mock-server.mjs`) на `localhost:3101`: четыре запроса API и настоящий Tus-сервер, файлы в `dev/.data`. Принимает данные медленно (`SPEED_MB`, по умолчанию 10 МБ/с), upload-токен живёт `TOKEN_TTL` секунд (по умолчанию 600). Остановить и запустить снова — это «сервер был недоступен».
- `npm run dev` — страница проверки (`dev/main.tsx`) на `localhost:5174`; `/api` проксируется на заглушку.
- `npm run typecheck` — проверка типов.

Порты 3001 и 5173 на этой машине заняты другими проектами, поэтому 3101 и 5174.

## Архитектурные правила

Подробности и обоснования — в спецификации (§5).

- Инстансами Uppy владеет только `UploadManager` (уровень приложения). Один инстанс на пакет.
- Очередь: одновременно активен один пакет. Временная ошибка — пакет держит очередь и повторяется сам; постоянная — пакет в `failed`, очередь идёт дальше; «Повторить» возвращает его в конец очереди, а не запускает параллельно.
- **Никогда не вызывать `uppy.destroy()` для пакета в cleanup эффекта.** Для незавершённых загрузок `destroy()`, `cancelAll()` и `removeFile()` отправляют `DELETE` на Tus-сервер. Использовать их только для осознанной отмены. Исключение — черновик формы: у него нет загрузок, его удаляет `useUploadDraft` при размонтировании.
- `UploadManager` — один экземпляр на уровне модуля, не в компоненте: `src/services/Uploader.ts` экспортирует `uploadManager`, остальные его импортируют. `new UploadManager` больше нигде не вызывать.
- Внешние функции (API, выдача upload-токена) читать через ref: опции Tus фиксируются при создании Uppy.
- `storeFingerprintForResuming: false`, без GoldenRetriever. Продолжение после закрытия вкладки — только через повторный выбор файлов и адреса загрузок, сохранённые с привязкой к пакету (§5.10). Токены в `localStorage` не хранить.
- В опциях Tus обязательны: сброс upload-токена при 401 и защита `HEAD` в `onAfterResponse` (иначе tus-js-client перезапускает загрузку с нуля).
- Повтор после недоступности сервера — забота `UploadManager` (пауза 10 с после каждой неудачной серии повторов tus, без ограничения числа попыток); встроенных `retryDelays` недостаточно.
- Не добавлять то, что уже делает Uppy или tus: троттлинг прогресса, нарастающие паузы между повторами, ожидание сети в офлайне.
- Тип файла проверяется по расширению в `onBeforeFileAdded`, с сохранением защиты от дублей. MIME не используем.
- Файлы живут только в черновике Uppy, форма (RHF) их не хранит. Объекты `File` не попадают в RHF, Redux или `localStorage`.
- Проверки на клиенте нужны только для удобства; сервер проверяет всё сам.
- Кнопки внутри `<form>` — `type="button"`, кроме submit.

## Работа с API Uppy

- API Uppy и tus-js-client «по памяти» ненадёжен: между 5.x и 6.x изменились импорты и поведение. Перед использованием метода или опции сверяйся с исходниками установленной версии: `node_modules/@uppy/*/src`, `node_modules/tus-js-client/lib`.
- Если поведение расходится с разделами спецификации, помеченными «(проверено в исходниках)», обнови спецификацию.
