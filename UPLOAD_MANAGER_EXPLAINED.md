## 1. Какую задачу решаем

Пользователи загружают через сайт большие данные: фотографии, видео, карты (формат MBTiles) и архивы. Один файл — до 25 ГБ, за один раз — до 100 ГБ. Такая загрузка может идти часами.

За несколько часов обязательно что-нибудь случится: пропадёт Wi-Fi, ноутбук уснёт, сервер перезагрузят. Поэтому главное требование звучит так:

> **После обрыва загрузка должна продолжиться с того места, где остановилась, а не начаться заново.**

Представьте: вы три часа загружали 20 ГБ, на 19-м гигабайте моргнул интернет — и всё сначала. Именно этого мы не допускаем.

## 2. Немного основ: браузер, сервер, запрос

- **Браузер** — программа у пользователя: Chrome, Firefox, Edge. В нём работает наш сайт — код на TypeScript и React. Это **фронтенд**, наша часть.
- **Сервер** — компьютер в дата-центре. Он принимает файлы и сохраняет их на диск. Это **бэкенд**, его делает бэкенд-разработчик.
- **Запрос** — сообщение от браузера серверу. Похоже на письмо: «Вот тебе кусок файла» или «Сколько ты уже получил?».
- **Ответ** — письмо обратно. В нём есть **код ответа** — число, по которому понятно, как дела:
  - `200`–`299` — всё в порядке;
  - `401` — «Не узнаю тебя, покажи свежий пропуск»;
  - `403` — «Тебе сюда нельзя»;
  - `404` — «Такого у меня нет»;
  - `500`–`599` — «У меня, у сервера, что-то сломалось».
- **nginx** — «вахтёр» перед сервером. Он принимает все запросы из интернета и передаёт их серверу. Если сам сервер в этот момент не работает, nginx отвечает `502`.

## 3. Почему большой файл нельзя просто «отправить»

Обычно файл отправляют одним запросом: «вот весь файл целиком». Для фотографии на 3 МБ это нормально. Для файла на 25 ГБ — плохо:

- если связь оборвалась посередине, обычный сервер выбрасывает всё полученное: запрос ведь не завершился;
- браузеру приходится отправлять файл заново, с нуля.

**Аналогия.** Вы диктуете по телефону книгу на 500 страниц. На 300-й странице связь прервалась. Если собеседник не записал, где вы остановились, придётся начинать с первой страницы.

## 4. Tus — загрузка «с закладкой»

**Tus** — это договорённость (по-научному *протокол*) между браузером и сервером: как загружать файл так, чтобы после обрыва продолжить. Сервер всё время помнит, сколько байт файла уже получил, — как **закладка в книге**.

Как это выглядит:

1. Браузер: «Хочу загрузить файл на 20 ГБ» (запрос `POST`).
   Сервер: «Хорошо, вот его адрес». Адрес — как номер заказа: по нему дальше ищут именно этот файл.
2. Браузер отправляет содержимое файла (запрос `PATCH`). Сервер записывает данные на диск и двигает закладку.
3. Связь оборвалась.
4. Браузер: «Сколько у тебя уже есть по этому адресу?» (запрос `HEAD`).
   Сервер: «12 ГБ».
5. Браузер отправляет оставшиеся 8 ГБ, начиная с 12-го.

Важно: **закладку хранит сервер**. Браузер не гадает, сколько успел отправить, а спрашивает. Поэтому продолжение точное.

## 5. Uppy — тележка для файлов

**Uppy** — готовая библиотека для загрузки файлов в браузере. Мы не пишем всё с нуля, а пользуемся ей.

Один экземпляр Uppy (он создаётся командой `new Uppy()`) удобно представлять как **тележку**:

- в неё складывают файлы;
- она проверяет правила, например «не больше 25 ГБ»;
- она знает про каждый файл: загружается ли он, сколько процентов готово, была ли ошибка.

Сама тележка файлы не возит. Для этого к ней подключают **плагин** — дополнение. У нас это плагин **Tus**: он умеет загружать «с закладкой». Можно представить его как водителя тележки, который знает правила Tus.

```ts
const uppy = new Uppy({ ... }); // тележка с правилами
uppy.use(Tus, { ... });         // посадили водителя, который возит по правилам Tus
```

## 6. Пакет (batch) — посылка из нескольких коробок

Пользователь загружает не один файл, а сразу несколько, и они связаны между собой:

- **многотомный архив** — `data.z01`, `data.z02`, `data.zip`. По отдельности тома бесполезны, как отдельные тома энциклопедии;
- **серия фотографий** одной съёмки.

К тому же пользователь один раз заполняет **метаданные** — описание загрузки (тип данных и другие поля формы). Они относятся ко всей загрузке, а не к каждому файлу.

Поэтому единица работы у нас — **пакет** (по-английски *batch*). Аналогия — **посылка из нескольких коробок с одной накладной**:

| В посылке | У нас |
|---|---|
| Коробки | Файлы |
| Накладная | Метаданные |
| Номер отправления | `batchId` — его выдаёт сервер |
| Номер коробки в посылке | `fileIndex` — 0, 1, 2… |

Каждый файл, уходя на сервер, несёт с собой `batchId` и `fileIndex`. Так сервер понимает, к какой посылке относится файл и какой он в ней по счёту.

**Для каждого пакета — своя тележка Uppy.** Так посылки не перепутаются, лимит «100 ГБ за раз» считается для каждой посылки отдельно, а отмена одной не трогает другие.

## 7. Черновик — посылку ещё собирают

Пока пользователь заполняет форму и выбирает файлы, посылка ещё не отправлена. Это **черновик** — как корзина в интернет-магазине до оформления заказа.

- Черновик — это просто тележка Uppy с файлами. На сервер пока ничего не ушло.
- Пользователь закрыл форму, не нажав «Загрузить», — черновик выбрасываем (`discardDraft`). Ничего страшного: на сервере его нет.
- Пользователь нажал «Загрузить» — черновик **становится пакетом** (`startBatch`). Это та же самая тележка с теми же файлами.

## 8. Зачем нужен UploadManager — диспетчер

Сайт сделан на **React**. В React интерфейс собирается из **компонентов** — кирпичиков вроде «форма», «кнопка», «список». Компоненты появляются на экране и исчезают. Например, модальное окно: открыли — компонент появился, закрыли — исчез.

**Проблема.** Если хранить загрузку внутри компонента формы, то при закрытии окна компонент исчезает **вместе с загрузкой**. Двадцать гигабайт — коту под хвост. Документация Uppy прямо об этом предупреждает.

**Решение.** Загрузками управляет отдельный объект — **UploadManager**. Это **диспетчер службы доставки**:

- он создаётся один раз при запуске сайта и живёт, пока открыта вкладка;
- компоненты приходят и уходят, а диспетчер остаётся и следит за всеми посылками;
- форма лишь передаёт ему посылку: «Вот, отправь».

```ts
// В коде приложения — один раз на всё приложение, НЕ внутри компонента:
export const uploadManager = new UploadManager({ tusEndpoint: '/api/uploads/', api });
```

Что умеет диспетчер:

| Действие | Метод |
|---|---|
| Выдать пустую тележку для формы | `createDraft()` |
| Выбросить черновик, если форму закрыли | `discardDraft(uppy)` |
| Оформить и отправить посылку | `startBatch(uppy, данныеФормы)` |
| Повторить загрузку (кнопка «Повторить») | `retryBatchNow(batchId)` |
| Отменить загрузку (кнопка «Отменить») | `cancelBatch(batchId)` |
| Сообщать интерфейсу об изменениях | `subscribe` и `getSnapshot` |

## 9. Очередь — одна погрузочная рампа

Пользователь может отправить несколько посылок подряд, не дожидаясь первой. Что тогда? По просьбе аналитика — **очередь**.

**Аналогия.** На складе **одна погрузочная рампа**. Грузится одна посылка, остальные ждут. Но саму посылку грузят **4 грузчика сразу**: 4 файла пакета загружаются одновременно (настройка `limit: 4`).

Почему не все посылки сразу:

- интернет-канал у пользователя один, и он делится между всеми загрузками. Если грузить всё одновременно, всё закончится примерно в одно время, но поздно. По очереди первая посылка придёт раньше — и сервер раньше начнёт её обрабатывать;
- чем меньше одновременных соединений, тем спокойнее серверу и браузеру.

Порядок очереди — это порядок, в котором пакеты лежат в поле `batches`. Это `Map` — список «ключ → значение», который помнит порядок добавления. Кто раньше добавлен, тот раньше грузится.

Правило очереди одно:

> **Одновременно активен только один пакет.**

За это отвечает метод `startNext()`: «если сейчас никто не грузится — возьми первого ожидающего и запусти».

## 10. Статусы пакета

У каждого пакета есть статус — поле `phase`:

| Статус | По-человечески | Аналогия |
|---|---|---|
| `queued` | Ждёт своей очереди | Посылка стоит у рампы |
| `uploading` | Файлы загружаются | Грузчики носят коробки |
| `completing` | Всё загружено, сообщаем серверу | Звоним на склад: «Всё привезли» |
| `failed` | Ошибка, нужен человек | Склад не принимает, ждём решения отправителя |

```text
queued ──► uploading ──► completing ──► готово (пакет исчезает из списка)
               │              │
               ▼              ▼
             failed ◄─────────┘
               │
               └── кнопка «Повторить» ──► queued (в конец очереди)
```

Кроме статуса у пакета есть:

- флаг **«ждём повтора»** (`waitingRetry`): нет связи, скоро попробуем снова;
- **текст ошибки** (`error`), если случилась ошибка, которую повтор не исправит.

Когда пакет загружен и сервер это подтвердил, диспетчер убирает пакет из своего списка. Дальше сервер сам распаковывает архивы и копирует данные куда нужно — это уже не забота браузера.

В минимальной версии на этом всё: пакет пропадает из списка. Показывать, чем закончилась обработка на сервере («Обработка», «Готово»), будем позже.

## 11. Ошибки и повторы

### Два вида ошибок

**Временные** — «сейчас не вышло, но потом получится»: пропал интернет, сервер перезагружается, nginx ответил `502`. Повторять имеет смысл.

**Постоянные** — «сколько ни повторяй, не поможет». Например, `403` — нет доступа. Тут нужен человек.

Какая ошибка какая, решает функция `isRetryable` по коду ответа. Временными считаются: сервер вообще не ответил, `401` (пропуск обновится), `408`, `409`, `423`, `429` и все `5xx`.

### Повторы — два уровня

**Аналогия.** Вы звоните в офис, а там занято.

1. **Сначала tus перезванивает сам**, несколько раз подряд: через 0,1 с, 1 с, 3 с и 5 с. Это встроенная функция плагина, всего около 9 секунд.
2. **Если так и не дозвонились, за дело берётся диспетчер.** Он ждёт 10 секунд и запускает новую попытку, которая снова начинается с быстрых повторов tus. Получается цикл примерно по 20 секунд, и так без ограничения числа попыток: если сервер выключили на час, через час загрузка продолжится сама.

### Как ведёт себя очередь при ошибке

- **Временная ошибка** — пакет **держит очередь** и ждёт. Логика простая: если пропал интернет, следующий пакет тоже не загрузится, переключаться на него нет смысла.
- **Постоянная ошибка** — пакет переходит в `failed` и **отпускает очередь**, следующие пакеты грузятся дальше. Загрузки идут часами, пользователь может отойти от компьютера, и одна сломанная посылка не должна держать остальные до его возвращения.
  Тонкость: в `failed` пакет переходит, только когда **ни один его файл уже не загружается**. Иначе два пакета какое-то время грузились бы одновременно.
- Кнопка **«Повторить»** у пакета с ошибкой ставит его **в конец очереди**, а не запускает сразу. Так правило «один активный пакет» не нарушается.

## 12. Токен — пропуск на склад

Сервер не принимает файлы от кого попало. Каждый запрос должен нести **токен** — электронный пропуск. Он кладётся в специальное поле запроса (заголовок): `Authorization: Bearer <токен>`.

Обычный пропуск пользователя живёт недолго, а загрузка 100 ГБ может длиться дольше. Поэтому для загрузки сервер выдаёт **отдельный пропуск на конкретную посылку** — upload-токен:

- он действует только для загрузки файлов этого пакета;
- живёт долго;
- выдаётся запросом `issueUploadToken(batchId)`.

Как с ним работает диспетчер (метод `getUploadToken`):

- первый раз спрашивает пропуск у сервера и запоминает его, чтобы не спрашивать перед каждым запросом;
- если сервер ответил `401` («пропуск устарел»), диспетчер забывает старый пропуск, и следующий запрос получит новый;
- когда пакет загружен или отменён, пропуск выбрасывается.

## 13. Главная ловушка: «начать сначала»

Это самое хитрое место в коде, поэтому подробно.

Напомню: после обрыва tus спрашивает сервер «Сколько у тебя есть?» (запрос `HEAD`). Мы проверили в коде библиотеки и тестом: **если на этот вопрос сервер ответил ошибкой (любой, кроме одного особого кода — `423`), tus решает, что старой загрузки больше нет, и начинает файл заново, с нуля.**

Когда так бывает на ровном месте:

- сервер перезагружается, и nginx отвечает `502` — сервер всего минуту недоступен, а закладка у него цела;
- пропуск устарел — `401`.

В обоих случаях закладка на сервере есть, а tus её выбросит и начнёт заново.

**Аналогия.** Вы перезвонили уточнить, на какой странице остановились, а секретарь сказал «Подождите минутку». А tus в этот момент кладёт трубку и начинает диктовать книгу с первой страницы.

Защита — в методе `createDraft`, в настройке `onAfterResponse`:

```ts
if (req.getMethod() === 'HEAD' && (status === 401 || status >= 500)) {
  throw new Error(`tus: HEAD вернул ${status}`);
}
```

Мы «выбрасываем ошибку» (`throw`). Tus воспринимает это как обычный сбой связи и просто **переспрашивает чуть позже**, не трогая закладку. Тест показал: без этих трёх строк короткий сбой сервера заставлял файл загружаться заново, а с ними — нет.

## 14. Как UploadManager разговаривает с React

React перерисовывает экран, когда меняются данные. Но UploadManager — обычный объект, и React о нём ничего не знает. Как сообщить React, что прогресс вырос?

Через **подписку**, как на рассылку:

1. Компонент говорит диспетчеру: «Сообщай мне об изменениях» — это `subscribe`.
2. Когда что-то меняется, диспетчер вызывает `notify()`: «Подписчики, есть новости».
3. Компонент забирает свежий **снимок** состояния — `getSnapshot()`. Снимок — как фотография: список пакетов с прогрессом и статусами на этот момент.

В React для этого есть готовый механизм `useSyncExternalStore`. Мы завернули его в простой хук:

```ts
const batches = useUploadBatches(uploadManager); // список пакетов, всегда свежий
```

Прогресс меняется очень часто, но Uppy сам присылает его не чаще двух раз в секунду. Поэтому экран не перерисовывается лишний раз.

Второй хук — `useUploadDraft(uploadManager)`. При открытии формы он берёт у диспетчера пустую тележку, а при закрытии выбрасывает её, если посылку так и не отправили.

## 15. Весь путь пакета по шагам

1. **Пользователь открывает форму.** `useUploadDraft` получает у диспетчера черновик — пустую тележку (`createDraft`).
2. **Перетаскивает файлы.** Зона перетаскивания кладёт их в тележку. Тележка проверяет правила: формат и размер. Неподходящие файлы не берёт, а пользователь видит причину.
3. **Нажимает «Загрузить».** Форма вызывает `startBatch(draft, { dataType, metadata })`.
4. **Оформление.** Диспетчер отправляет на сервер «накладную»: метаданные и список файлов (`createBatch`). Сервер отвечает номером посылки — `batchId`.
5. **Подписываем коробки.** Диспетчер записывает в каждый файл `batchId` и `fileIndex` и ставит пакет в очередь (`queued`). Форму уже можно закрыть.
6. **Старт.** `startNext()`: если никто не грузится, запускаем этот пакет (`run` → `uppy.upload()`). Статус — `uploading`.
7. **Загрузка.** Перед каждым запросом подставляется пропуск (`getUploadToken`). Файлы летят на сервер по 4 одновременно, прогресс идёт в интерфейс.
8. **Пропал интернет.** Tus повторяет несколько раз, не выходит — диспетчер включает автоповтор: пауза 10 секунд, новая попытка, и так по кругу. В интерфейсе: «Нет связи с сервером. Повторим автоматически».
9. **Интернет вернулся.** На очередном повторе tus спрашивает «Сколько у тебя есть?», получает ответ и докачивает остаток.
10. **Все файлы загружены.** Диспетчер сообщает серверу «всё привезли» (`completeBatch`). Статус — `completing`.
11. **Сервер подтвердил.** Диспетчер убирает пакет (`remove`), выбрасывает пропуск и запускает следующий пакет из очереди.

## 16. Экскурсия по коду UploadManager.ts

Пройдём файл сверху вниз. Удобно открыть его рядом.

### Поля — что диспетчер помнит

```ts
private readonly batches = new Map<string, Batch>();          // все пакеты в порядке очереди
private readonly submitted = new WeakSet<Uppy>();              // черновики, которые уже отправлены
private readonly tokens = new Map<string, Promise<string>>();  // пропуска по пакетам
private readonly listeners = new Set<() => void>();            // подписчики (компоненты React)
private snapshot: BatchView[] = [];                            // последний снимок для интерфейса
```

- `Map` — список «ключ → значение». Ключ — номер посылки (`batchId`).
- `WeakSet` — набор объектов, который не мешает браузеру освободить память, когда объект больше не нужен. Он помогает отличить «черновик ещё в форме» от «черновик уже отправлен».
- `Promise<string>` — «обещание строки». Пропуск может ещё быть в пути с сервера. Если два запроса попросят пропуск одновременно, оба дождутся одного и того же ответа, и сервер не спросят дважды.

### `constructor` — при создании

Вешает обработчик `beforeunload`: если пользователь закрывает вкладку, пока есть незавершённые загрузки, браузер спросит «Точно уйти?».

### `createDraft` — выдать тележку

Создаёт Uppy с правилами:

- `restrictions` — лимиты 25 ГБ на файл и 100 ГБ на пакет;
- `onBeforeFileAdded` — «проверка на входе»: не брать тот же файл второй раз и не брать неподходящий формат;
- плагин Tus с настройками: адрес сервера, 4 файла одновременно, пропуск в каждом запросе, повтор при `401` и защита от «начать сначала» (раздел 13).

### `discardDraft` — выбросить черновик

Удаляет тележку, если её ещё не отправили. Если уже отправили (она в `submitted`), не трогает: это уже пакет.

### `startBatch` — оформить посылку

Это шаги 3–6 из предыдущего раздела. Одна тонкость: черновик помечается как отправленный **до** запроса к серверу. Если пользователь закроет форму, пока ждём ответ, тележку не выбросят. Если сервер ответил ошибкой, пометку снимаем, а форма показывает ошибку.

Здесь же диспетчер подписывается на **события** тележки — сообщения, которые Uppy присылает сам:

- `progress` — прогресс изменился → обновить интерфейс;
- `upload-success` — файл загружен → если загружены все, вызвать `complete`;
- `upload-error` — файл не загрузился даже после повторов tus → вызвать `handleError`.

### `startNext` и `run` — очередь

- `startNext` проверяет, есть ли активный пакет (`uploading` или `completing`). Если есть — ждём. Если нет — берём первый `queued` и запускаем.
- `run` запускает или продолжает пакет. Если все файлы уже загружены — сразу `complete`. Иначе вызывает `uppy.upload()`: Uppy сам перезапустит файлы с ошибкой (с того места, где они остановились) и начнёт ещё не начатые.

### `complete` — «всё привезли»

Сообщает серверу о завершении (`completeBatch`). Получилось — убираем пакет, выбрасываем пропуск и запускаем следующий. Не получилось — `handleError`, как с любой другой ошибкой.

### `handleError` и `failIfStuck` — что делать с ошибкой

- Временная ошибка — ставим таймер на 10 секунд. Таймер один на пакет, даже если упали сразу несколько файлов.
- Постоянная — запоминаем текст ошибки и отменяем таймер.
- `failIfStuck` проверяет: есть постоянная ошибка, и ни один файл уже не загружается? Тогда пакет переходит в `failed`, и запускается следующий.

### `retryBatchNow` — кнопка «Повторить»

- Пакет в очереди — ничего не делаем: он и так стартует в свой черёд.
- Пакет в `failed` — переносим в конец очереди.
- Активный пакет — повторяем сразу, не дожидаясь таймера. Этот же метод вызывает и таймер автоповтора.

### `cancelBatch` — кнопка «Отменить»

Убирает пакет (`remove` → `uppy.destroy()`: Uppy остановит загрузку и попросит сервер удалить недогруженные файлы), запускает следующий пакет, сообщает серверу об отмене и выбрасывает пропуск.

### Помощники

- `remove` — убрать пакет из списка и остановить его тележку;
- `clearRetry` — отменить напоминание о повторе;
- `notify` — сделать новый снимок и сообщить подписчикам;
- `toView` — превратить внутренний пакет в данные для интерфейса: сколько файлов, сколько байт загружено, есть ли ошибка;
- `isRetryable` — решить, временная ли ошибка.

## 18. Как этим пользоваться

### Подключить

```ts
// 1. Один раз на всё приложение — в отдельном модуле, у нас это src/services/Uploader.ts.
//    Остальные файлы делают import { uploadManager } from '…/services/Uploader'.
//    http — HTTP-клиент вашего приложения; при ошибке он должен выбрасывать ошибку с полем status.
export const uploadManager = new UploadManager({
  tusEndpoint: '/api/uploads/', // точный путь даст бэкенд
  api: {
    createBatch: (input) => http.post('/api/batches', input),
    issueUploadToken: (batchId) =>
      http.post(`/api/batches/${batchId}/upload-token`).then((response) => response.token),
    completeBatch: (batchId) => http.post(`/api/batches/${batchId}/complete`),
    cancelBatch: (batchId) => http.delete(`/api/batches/${batchId}`),
  },
});
```

```tsx
// 2. В модальном окне — форма. После отправки окно закрываем.
<UploadForm manager={uploadManager} onSubmitted={closeModal} />

// 3. Где-нибудь на странице — список текущих загрузок.
<BatchList manager={uploadManager} />
```

### Частые изменения

| Нужно | Где |
|---|---|
| Поменять лимиты | `fileRules.ts`: `MAX_FILE_SIZE`, `MAX_BATCH_SIZE`. И сказать бэкенду: у него те же лимиты |
| Добавить формат | `fileRules.ts`: массив `ALLOWED_NAME_PATTERNS` |
| Сколько файлов грузить одновременно | `UploadManager.ts`, `createDraft`: настройка `limit` |
| Как часто повторять, если сервер недоступен | `UploadManager.ts`: `RETRY_INTERVAL` |

### Чего делать нельзя

- **Создавать `UploadManager` внутри компонента.** Загрузка будет пропадать вместе с компонентом.
- **Вызывать `uppy.destroy()` у пакета «просто так»**, например при закрытии окна. Это остановит загрузку и удалит недогруженные файлы на сервере.
- **Убирать защиту `HEAD`** в `onAfterResponse`. Вернётся «начать сначала».
- **Класть сами файлы (`File`) в состояние формы или в `localStorage`.** Файлы огромные; они живут только в тележке Uppy.

## 19. Почему решения именно такие

| Решение | Почему |
|---|---|
| Протокол Tus | Даёт продолжение с места остановки — это главное требование |
| Готовая библиотека Uppy | Проверки файлов, прогресс, повторы и работа с Tus уже готовы и проверены |
| UploadManager вне компонентов | Закрытие окна не должно обрывать загрузку |
| Пакет вместо отдельных файлов | Тома архива и метаданные — одно целое |
| Своя тележка Uppy на каждый пакет | Пакеты не путаются, лимит 100 ГБ считается на пакет, отмена одного не трогает другие |
| Очередь пакетов | Просьба аналитика; первая посылка приходит раньше; меньше нагрузка |
| Свой автоповтор (пауза 10 секунд) | Встроенные повторы tus сдаются примерно за 9 секунд, а нужно продолжить, когда сервер вернётся, — хоть через час |
| Отдельный пропуск на загрузку | Загрузка может длиться дольше, чем живёт обычный пропуск пользователя |
| Защита `HEAD` | Без неё короткий сбой сервера заставлял загружать файл с нуля (проверено тестом) |
| Файл отправляется целиком, а не кусками | Так советует документация Uppy и tus: куски нужны, только если сервер ограничивает размер запроса. При обрыве сервер сохраняет всё, что успел получить (если nginx настроен, как договорились с бэкендом) |
| Загрузки не запоминаются в `localStorage` | Продолжение после закрытия вкладки пока не требуется, а старые записи только мешали бы |

## 20. Что будет, если…

| Ситуация | Что произойдёт |
|---|---|
| Закрыли модальное окно во время загрузки | Ничего страшного: загрузка продолжается, её видно в списке загрузок |
| Закрыли окно прямо во время отправки формы | Загрузка всё равно начнётся |
| Пропал интернет на минуту | «Нет связи с сервером. Повторим автоматически». Связь вернулась — загрузка продолжается с того же места |
| Сервер перезагрузили | То же самое |
| Пропуск на загрузку устарел | Диспетчер незаметно получает новый и продолжает |
| Сервер ответил «нет доступа» | Пакет в статусе «ошибка», следующие загружаются дальше. Можно нажать «Повторить» или «Отменить» |
| Нажали «Отменить» | Загрузка останавливается, данные на сервере удаляются, стартует следующий пакет |
| Закрыли вкладку браузера | Браузер спросит «Точно уйти?». Если уйти, загрузка прервётся: продолжение после закрытия вкладки пока не сделано |
| Отправили второй пакет, пока грузится первый | Второй ждёт в очереди и стартует сам |
| Пакет загрузился | Сервер подтвердил — пакет пропадает из списка текущих загрузок |
| Бросили файл мимо зоны, пока открыта форма | Ничего: браузер не откроет файл и не уйдёт со страницы |

## 21. Словарик

| Слово | Значение |
|---|---|
| Браузер | Программа, в которой открыт сайт |
| Сервер | Удалённый компьютер, который принимает файлы |
| Фронтенд / бэкенд | Код в браузере (наш) / код на сервере |
| Запрос / ответ | Сообщение браузера серверу и ответ сервера |
| Код ответа | Число в ответе: 200 — хорошо, 401 — нужен новый пропуск, 403 — нельзя, 5xx — сбой сервера |
| API | Набор запросов, которые понимает сервер |
| Токен | Электронный пропуск, который прикладывается к запросу |
| Tus | Правила загрузки «с закладкой» |
| Смещение (offset) | «Закладка»: сколько байт файла сервер уже получил |
| Uppy | Библиотека загрузки файлов; один её экземпляр — «тележка» с файлами |
| Плагин | Дополнение к Uppy; плагин Tus возит файлы по правилам Tus |
| Пакет (batch) | Одна загрузка: несколько файлов плюс метаданные |
| Метаданные | Описание загрузки: тип данных и другие поля формы |
| Черновик | Пакет до нажатия «Загрузить» |
| Очередь | Порядок, в котором загружаются пакеты |
| Событие | Сообщение, которое Uppy присылает сам: «файл загружен», «ошибка» |
| Компонент | Кусочек интерфейса на React: форма, кнопка, список |
| Хук | Функция React, которая подключает компонент к данным (`useUploadBatches`) |
| Монтирование / размонтирование | Компонент появился на экране / исчез с него |
| Promise, `async`/`await` | Способ работать с тем, что придёт не сразу, например с ответом сервера |
| Снимок (snapshot) | «Фотография» состояния загрузок для интерфейса |
