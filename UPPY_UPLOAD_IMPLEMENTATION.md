# Загрузка данных на внешний сервер: фронтенд на Uppy + Tus

> Спецификация фронтенда загрузки. React + TypeScript, react-hook-form, Uppy 6.x.
>
> Зона ответственности — **только фронтенд**. Бэкенд, nginx и сеть делают другие люди; §6 — список того, что фронтенд от них ожидает, его нужно передать им.
>
> Поведение Uppy, помеченное **(проверено в исходниках)**, сверено с `@uppy/core` 6.2.0, `@uppy/react` 6.0.0, `@uppy/tus` 6.0.0 и `tus-js-client` 4.3.1 (12.10.2026). При обновлении пакетов эти места нужно перепроверить.
>
> История: v1 — общее исследование темы; v2 — переработано под требования проекта; v3 (12.10.2026) — учтены ответы бэкенда и аналитика: лимиты, форматы, очередь пакетов, upload-токен, скрытые контуры, продолжение после закрытия вкладки; по оставшимся вопросам приняты допущения.

## 1. Контекст

### 1.1 Требования к системе

Из общего описания системы:

- **Данные.** Пользователь загружает через веб-приложение фотографии, MBTiles и видео. Данные могут быть упакованы в архивы zip и rar, в том числе многотомные или с логической нумерацией в имени файла.
- **Обработка.** Список «XXX pipeline», в которые копируются данные, задаётся конфигурацией. После успешного копирования в соответствующие контуры исходные данные удаляются с «внешнего» сервера.
- **Интерфейс.** Пользователь указывает обязательные и опциональные метаданные **перед** загрузкой и наблюдает текущий статус загрузки в веб-приложении.
- **Возобновление.** При потере соединения во время загрузки веб-приложение возобновляет загрузку после восстановления соединения с сервером.
- **Пользователи.** Учётные записи заводятся вручную в административной панели «Сервиса авторизации и аутентификации». Учётные данные выдаются лично, сменить пароль пользователь не может.
- **Сеть.** Веб-приложение доступно по HTTPS на порту 443; порты 80 и 443 открыты из внешней сети. API бэкенда для работы с данными работает по HTTPS на порту 8010 и проверяет Bearer-токен. Порт 8001 доступен только из сетей соответствующих контуров.
- **Объём.** До 500 ГБ в сутки по HTTPS в каждом направлении.

### 1.2 Ответы команды

**Бэкенд и инфраструктура:**
- Файлы пишутся на диск, а не в БД. Перед сервером стоит nginx; отключение буферизации запросов на адресе загрузки бэкенд добавит (§6.2).
- Tus-эндпоинт будет, вся работа с ним идёт через nginx (443). Точного пути пока нет (Q12). Порт 8010 нужен для стриминга и к загрузке не относится. Реализацию Tus-сервера выбирает бэкенд, для фронтенда она не важна. Когда эндпоинт появится, проверить расширения: `curl -i -X OPTIONS <url>` — в ответе `Tus-Version: 1.0.0` и `Tus-Extension` с `creation` и `termination`.
- Токен: бэкенд предложил два варианта — обновлять обычный access-токен во время загрузки или выдавать отдельный долгоживущий токен на загрузку. Выбран второй (D14), ждём подтверждения (Q13).
- Порядок «создать пакет → загрузить файлы → сообщить о завершении → опрашивать статус» согласован. Список метаданных фиксированный.

**Аналитик:**
- Лимиты: один файл — до 25 ГБ, вся загрузка — до 100 ГБ.
- Форматы: фото `.jpg`, `.jpeg`, `.png`, `.tiff` (и `.tif`); видео `.mp4`, `.mov`, `.mkv`, `.avi`, `.ts`; MBTiles `.mbtiles`; архивы zip (`.zip`, тома `.z01`, `.z02` … и `.zx01`) и RAR. RAR и MBTiles нужны — подтверждено отдельно.
- Метаданные определяются списком атрибутов для типа данных (Q6).
- Список pipeline задаётся настройками. Контуры пользователю недоступны, и он о них ничего не знает.
- Несколько загрузок — в очередь.
- После закрытия вкладки: показать, что есть неоконченная загрузка и её нужно продолжить. Если можно — продолжить с того же места без дополнительных действий. Если пользователю придётся выбирать файлы — показать, что загрузка прервана, и предложить загрузить заново (Q10).

**Фронтенд:**
- Форма загрузки может оказаться в модалке или табе, то есть **компонент может размонтироваться во время загрузки**.
- Формы на react-hook-form. Поле для файлов на форме одно.

### 1.3 Что из этого следует для фронтенда

| Требование | Следствие |
|---|---|
| Фото, видео, MBTiles, многотомные архивы | Одна загрузка — это **пакет из многих файлов**, а не один файл. Тома архива имеют смысл только вместе |
| Метаданные указываются перед загрузкой и зависят от типа данных | Сначала форма (тип данных, атрибуты, файлы), затем создание пакета на сервере, затем передача байтов. Метаданные принадлежат пакету |
| 25 ГБ на файл, 100 ГБ на загрузку | `restrictions.maxFileSize` и `maxTotalFileSize`; сервер проверяет те же лимиты |
| Несколько загрузок — в очередь | Пакеты передаются по одному, остальные ждут (D15) |
| Наблюдать статус; контуры скрыты от пользователя | Статус передачи (клиент) и обработки (сервер), но без упоминания контуров и pipeline (D16) |
| Возобновление после восстановления соединения **с сервером** | Tus плюс своя политика автоповтора: «браузер офлайн» и «браузер онлайн, но сервер недоступен» — разные случаи (§5.5) |
| Продолжение после закрытия вкладки желательно | Возможно только через повторный выбор тех же файлов (§5.10) |
| Многочасовые загрузки и Bearer-токен | Отдельный upload-токен на пакет (D14) |
| Tus через nginx на 443 | Тот же origin, что у веб-приложения: CORS не нужен |
| 500 ГБ/сутки | В среднем ≈ 5,8 МБ/с ≈ 46 Мбит/с непрерывно, пики выше. Для фронтенда влияет только на число файлов, загружаемых параллельно |

## 2. Принятые решения

| # | Решение | Почему |
|---|---|---|
| D1 | Транспорт — протокол Tus через `@uppy/tus` | Resume с подтверждённого сервером смещения |
| D2 | Единица работы — **пакет** (batch): тип данных, метаданные и N файлов | Многотомные архивы и наборы фото загружаются вместе |
| D3 | Инстансами Uppy владеет `UploadManager` на уровне приложения, а не UI-компонент | Закрытие модалки или таба не должно прерывать загрузку; `destroy()` удаляет загрузки на сервере (§5.3) |
| D4 | Один инстанс Uppy на пакет; черновик формы становится пакетом после отправки | Изоляция метаданных, отмены и статуса пакетов |
| D5 | Без GoldenRetriever и без глобальных отпечатков tus-js-client (`storeFingerprintForResuming: false`). Для продолжения после закрытия вкладки адреса загрузок храним сами, с привязкой к пакету (§5.10) | GoldenRetriever не сохраняет файлы больше 10 МиБ. Глобальные отпечатки не знают о пакетах и ведут к повторному использованию старых сессий |
| D6 | `chunkSize` и `retryDelays` — по умолчанию; `limit: 4` (одновременно загружаемых файлов пакета). В nginx для Tus — `proxy_request_buffering off` и `client_max_body_size 0` | Документация Uppy и tus-js-client: `chunkSize` задают, только если на пути есть ограничение размера тела запроса, иначе он вредит скорости. Если такое ограничение найдётся (CDN, другой прокси) — задать `chunkSize` ниже него. `limit` по умолчанию (20) велик для больших файлов, а по HTTP/1.1 браузер держит не больше 6 соединений на сервер — запросам к API не хватило бы места. Начинаем с 4, подбираем по замерам |
| D7 | Своя политика автоповтора в `UploadManager`: когда исчерпаны встроенные повторы tus (около 9 с), сетевые ошибки и 5xx повторяются через 10 с после каждой неудачной серии — цикл около 20 с, без ограничения числа попыток, пока пользователь не отменит пакет | Требование «возобновлять после восстановления соединения с сервером»; встроенные повторы tus заканчиваются. Нарастающие паузы уже есть у tus, поэтому у менеджера пауза постоянная |
| D8 | Защита `HEAD`-запроса в `onAfterResponse` | tus-js-client при не-2xx ответе на `HEAD` начинает загрузку файла заново с нуля (§5.5) |
| D9 | Проверка типа файла по расширению в `onBeforeFileAdded` | MIME у `.mbtiles`, `.rar` и томов архивов ненадёжен; `allowedFileTypes` не поддерживает шаблоны вроде `.z01…` |
| D10 | Файлы живут только в черновике Uppy; форма (react-hook-form) их не хранит, а наличие файлов проверяет при отправке | Один источник данных о файлах, без синхронизации Uppy и формы |
| D11 | Свой UI на хуках `@uppy/react` (`useDropzone`, `useUppyState`), без `@uppy/dashboard` и без готовых headless-компонентов (`Dropzone`, `FilesList`) | Дизайн-система и пакетная модель статусов. В готовых компонентах тексты зашиты на английском и не переводятся, стили — свои (Tailwind-классы `uppy:`) |
| D12 | После старта пакета отдельные файлы не удаляются — только отмена всего пакета | Манифест пакета согласован с сервером. Решение для MVP, можно пересмотреть |
| D13 | Комплектность многотомных архивов фронтенд проверяет только по именам файлов и только предупреждает, не блокирует. Можно отложить на после MVP | Содержимое файлов фронтенд не читает; полную проверку делает сервер. Предупреждение экономит пользователю часы загрузки неполного набора |
| D14 | Tus-запросы авторизуются отдельным **upload-токеном пакета**, а не access-токеном пользователя. Остальные вызовы API — обычным access-токеном через HTTP-клиент приложения | Загрузка 100 ГБ может идти дольше сессии пользователя. Upload-токен не зависит от обновления сессии, а его права ограничены одним пакетом |
| D15 | Очередь пакетов: активен один пакет, остальные в статусе `queued`. Пакет создаётся на сервере сразу при отправке формы, передача начинается, когда до него дойдёт очередь. При временной ошибке (нет связи) пакет держит очередь и повторяется сам. При постоянной ошибке пакет переходит в `failed` (когда ни один его файл уже не загружается) и отпускает очередь; «Повторить» ставит его в конец очереди | Ответ аналитика. Ошибки метаданных пользователь видит сразу, а не через часы. Без связи следующий пакет всё равно не загрузится, а постоянная ошибка одного пакета не должна держать остальные часами, пока пользователя нет у компьютера (Q15) |
| D16 | В интерфейсе нет ни выбора pipeline, ни статусов по контурам; обработка на сервере показывается одним статусом | Контуры пользователю недоступны, и он о них не знает |
| D17 | Лимиты: 25 ГБ на файл и 100 ГБ на пакет. ГБ считаем как ГиБ (1024³), как показывает Windows; сервер должен считать так же | Ответ аналитика |
| D18 | Паузы пакета нет | В требованиях её нет. Если понадобится: `uppy.pauseAll()`/`resumeAll()` плюс `retryAll()` для файлов с ошибкой |
| D19 | Сначала минимальная рабочая версия: форма (тип данных и файлы), загрузка с докачкой, очередь пакетов, прогресс и статус пакета («в очереди», «N из M», «нет связи», «ошибка»), «Повторить» и «Отменить». Позже: статус обработки на сервере, атрибуты по типам (Q6), продолжение после закрытия вкладки (§5.10), выход из системы (Q11), предупреждение о неполном архиве (D13), место в очереди, прогресс по файлам, скорость и оставшееся время | Сначала стабильная основа, потом остальное |

## 4. Архитектура

### 4.1 Поток данных

```text
Браузер                                     Внешний сервер                 Контуры
───────                                     ──────────────                 ───────
Форма (RHF): тип данных, атрибуты, файлы
  │ submit
  ├─ POST /api/batches ──────────────────► пакет создан: batchId
  │  (пакет в очереди)
  │
UploadManager → Uppy (пакет) → @uppy/tus
  ├─ POST /api/batches/{id}/upload-token ► upload-токен пакета
  ├─ POST/HEAD/PATCH (Tus) ──► nginx ────► Tus-сервер → диск
  │
  ├─ POST /api/batches/{id}/complete ────► проверка комплектности
  │                                        → распаковка и проверка
  │                                        → копирование в pipeline ─────► XXX pipeline 1..N
  │                                        → удаление исходных данных
  └─ GET /api/batches/{id} (опрос) ◄────── статус пакета (без деталей о контурах)
```

### 4.2 Жизненный цикл пакета

1. Пользователь открывает форму, выбирает тип данных, заполняет атрибуты и добавляет файлы. Файлы попадают в черновой инстанс Uppy; на сервер ничего не уходит.
2. Submit: валидация RHF → `createBatch`. Сервер проверяет метаданные, сохраняет манифест (упорядоченный список файлов) и возвращает `batchId`. Пакет встаёт в очередь (`queued`), модалку можно закрыть.
3. Когда очередь доходит до пакета, менеджер получает upload-токен, записывает `batchId` и `fileIndex` (номер файла в манифесте) в meta каждого файла (они уходят в `Upload-Metadata`) и запускает `uppy.upload()`.
4. Когда все файлы переданы, менеджер вызывает `completeBatch(batchId)` (идемпотентно, с повторами) и запускает следующий пакет из очереди.
5. Дальше статус приходит с сервера (опрос `getBatch`), пока пакет не перейдёт в конечное состояние. В минимальной версии этого нет (D19).

### 4.3 Контракт с бэкендом (порядок согласован, детали — предложение)

```http
POST   /api/batches                         {dataType, metadata, files: [{name, size}]} → {batchId}
POST   /api/batches/{batchId}/upload-token  → {token, expiresAt}
POST   <tus-endpoint>                       Tus; Authorization: Bearer <upload-токен>
                                            Upload-Metadata: batchId, fileIndex, filename, filetype
POST   /api/batches/{batchId}/complete      → 202, идемпотентно
GET    /api/batches/{batchId}               → {status, files[], error?}
GET    /api/batches                         → пакеты пользователя, включая незавершённые
DELETE /api/batches/{batchId}               → отмена пакета
```

ID генерирует сервер: `batchId` возвращается при создании пакета, а файл внутри пакета определяется по `fileIndex` — номеру в манифесте.

Сервер обязан:

- проверять, что `batchId` принадлежит пользователю, а `fileIndex` есть в манифесте и по нему ещё нет завершённой загрузки. Незавершённую можно заменить: если старая загрузка удалена или истекла, фронт создаёт её заново. Метаданные Tus присылает клиент, доверять им нельзя;
- сверять `Upload-Length` с размером из манифеста и проверять лимиты (D17);
- принимать `complete` только когда все файлы манифеста загружены полностью;
- вести статусы пакета: `created → uploading → uploaded → processing → done | failed | canceled | expired`. Ни статусы, ни тексты ошибок не должны упоминать контуры и pipeline (D16).

## 5. Фронтенд

### 5.1 Слои

Код — `src/upload/`:
- `UploadManager.ts` — менеджер загрузок; `types.ts` — типы; `hooks.ts` — хуки для React;
- `src/services/Uploader.ts` — единственный экземпляр менеджера и запросы к API (`uploadManager`); при переносе в приложение запросы переводятся на его HTTP-клиент;
- `fileRules.ts` — форматы и лимиты; `formatSize.ts` — размер файла для людей;
- `components/` — `UploadForm`, `FileDropzone`, `FileList`, `BatchList` с минимальными стилями.

Интерфейсы описаны в коде; здесь — устройство и правила.

```text
uploadManager (один экземпляр на уровне модуля)   ← инстансы Uppy, очередь, токены, автоповтор, beforeunload
App
├─ UploadModal / Tab
│  └─ UploadForm (RHF)                          ← useUploadDraft(): черновик на время жизни формы
│     ├─ тип данных и его атрибуты
│     └─ FileDropzone + FileList                ← работают с черновиком (Uppy)
└─ BatchList                                    ← useUploadBatches(): загрузки этой вкладки
```

- **UploadManager** — обычный класс, не React-компонент. Один экземпляр создаётся на уровне модуля, поэтому ему не страшны ни повторные рендеры, ни StrictMode. Отвечает только за передачу: создаёт и уничтожает инстансы Uppy, ведёт очередь, upload-токены, автоповтор и `beforeunload`, вызывает `completeBatch`. Наружу отдаёт снимок активных пакетов (`subscribe` и `getSnapshot` для `useSyncExternalStore`) и действия `createDraft`, `discardDraft`, `startBatch`, `retryBatchNow`, `cancelBatch`.
- **Статус обработки на сервере** UI получает сам через `getBatch` и `listBatches` обычным для приложения способом (например, опросом). В минимальной версии этого нет (D19). В снимке менеджера только пакеты, которые ещё передаются с этой вкладки: после `completeBatch` или отмены пакет из него исчезает.
- **UI-компоненты** пакетами Uppy не управляют. Исключение — черновик (это сам инстанс Uppy): `FileDropzone` и список файлов формы работают с ним через `useDropzone` и `useUppyState`.
- **Форма** знает только про черновик. Черновик живёт, пока смонтирована форма (`useUploadDraft`).

### 5.2 Внешние зависимости

В конструктор менеджера передаются `tusEndpoint` (Q12) и `api` — функции `createBatch`, `issueUploadToken`, `completeBatch` и `cancelBatch`. Их реализует приложение поверх своего HTTP-клиента с access-токеном пользователя. Контракт: если сервер ответил ошибкой, функция отклоняется с ошибкой, у которой есть поле `status`; по нему менеджер отличает временные ошибки от окончательных.

Менеджер живёт всё время работы приложения, поэтому зависимости должны быть стабильными: функции модуля, а не замыкания из компонентов.

Если бэкенд выберет вариант с обычным access-токеном (Q13), `issueUploadToken` заменяется получением access-токена, остальная схема не меняется.

### 5.3 Жизненный цикл Uppy (проверено в исходниках)

- **Не вызывать `uppy.destroy()` в cleanup эффекта.** `destroy()` вызывает `cancelAll()`, тот — `removeFiles()`, и для незавершённых загрузок Tus-плагин выполняет `upload.abort(true)`, то есть отправляет `DELETE` на сервер. Закрытие модалки удалило бы уже загруженные гигабайты. Вдобавок в StrictMode cleanup срабатывает сразу после первого монтирования, и компонент продолжит работать с уничтоженным инстансом.
- `removeFile()` и `cancelAll()` для незавершённой загрузки тоже отправляют `DELETE` (если сервер поддерживает расширение termination). Вызывать их только как осознанную отмену.
- Для завершённого файла `DELETE` не уходит: после `upload-success` плагин снимает свои обработчики. Поэтому `destroy()` пакета после завершения передачи безопасен.
- `id` инстанса входит в ID файла (`generateFileID`), а значит, и в отпечаток Tus: `tus-${file.id}-${endpoint}`. Берём `id: crypto.randomUUID()`: уникальность нужна `useDropzone`, который ищет свой `<input>` по этому id; стабильность между перезагрузками не нужна (D5).
- Черновик можно уничтожать при размонтировании формы: на сервере у него ничего нет. `startBatch` забирает черновик до запроса, поэтому закрытие формы во время отправки загрузку не отменяет.
- Завершение передачи пакета определяется по состоянию всех файлов (`progress.uploadComplete`), а не по событию `complete`: `retryUpload()` запускает отдельный прогон, и `complete` приходит по каждому повтору отдельно.

### 5.4 Пакеты и конфигурация Uppy и Tus

```bash
npm install @uppy/core@6 @uppy/react@6 @uppy/tus@6 react-hook-form
```

Точные версии зафиксировать в `package.json`. В Uppy 6 пакеты `@uppy/utils`, `@uppy/store-default` и `@uppy/companion-client` объединены с `@uppy/core`: импорт теперь из `@uppy/core/utils` и аналогичных подпутей. `@uppy/golden-retriever`, `@uppy/dashboard` и `@uppy/aws-s3` не нужны.

Конфигурация Uppy и Tus — метод `createUppy` в `src/upload/UploadManager.ts`. Главное:

- лимиты D17 и проверка формата в `onBeforeFileAdded` с защитой от дублей;
- `chunkSize` и `retryDelays` по умолчанию, `limit: 4` (D6), `storeFingerprintForResuming: false` (D5);
- `batchId` — общая meta инстанса (`uppy.setMeta`), `fileIndex` — meta файла; обе уходят в `Upload-Metadata`;
- `onBeforeRequest` подставляет upload-токен; `onAfterResponse` сбрасывает его на 401 (следующий запрос получит новый) и защищает `HEAD` (D8). В `Upload-Metadata` уходят все meta файла — это поведение Uppy по умолчанию.

- Порядок проверок при добавлении файла (проверено в исходниках): сначала `onBeforeFileAdded`, затем `maxFileSize`, затем `maxTotalFileSize`. Отказы приходят событием `restriction-failed`; тексты для пользователя формируем свои — встроенные сообщения Uppy на английском.
- Если перевыпустить upload-токен не удалось (например, закончилась сессия), это считается временной ошибкой, и менеджер продолжает повторы. На 401 от API реагирует HTTP-клиент приложения обычным способом. Если вход выполняется без перезагрузки страницы, загрузка продолжится сама; если с перезагрузкой — работает сценарий §5.10.
- Неисправимая ошибка (4xx, кроме перечисленных в §5.5) останавливает автоповтор пакета до действия пользователя: «Повторить» или «Отменить». Когда ни один файл пакета уже не загружается, пакет переходит в `failed` и очередь идёт дальше (D15).

**Про `chunkSize` (D6).** По умолчанию он равен `Infinity`: остаток файла уходит одним `PATCH`. При обрыве Tus-сервер сохраняет всё, что успел получить, и загрузка продолжается с этого места. Это работает, только если nginx передаёт тело запроса сразу (`proxy_request_buffering off`) и не ограничивает его размер (`client_max_body_size 0`). Если nginx буферизует запрос, при обрыве на 3 ГБ сервер не получит ничего, и загрузка начнётся с нуля. Проверить на этапе 1.

### 5.5 Возобновление: кто за что отвечает (проверено в исходниках)

| Ситуация | Что делают Uppy и tus-js-client | Что делаем мы |
|---|---|---|
| Кратковременный сбой запроса | tus-js-client повторяет по `retryDelays`; если после повтора смещение выросло, счётчик попыток сбрасывается | — |
| Браузер офлайн (`navigator.onLine === false`) | Свой `onShouldRetry` в `@uppy/tus` ставит очередь на паузу и ждёт события `online`, затем `HEAD` и продолжение с серверного смещения | — |
| Браузер «онлайн», а сервер недоступен (рестарт, 502 от nginx, VPN, «Wi-Fi без интернета») | События `online` и `back-online` не наступают; попытки из `retryDelays` заканчиваются, файл получает `error` | Автоповтор менеджера (D7): через 10 с после неудачи — снова `uppy.upload()` (он перезапускает файлы с ошибкой), и так без ограничения числа попыток; вместе с повторами tus цикл около 20 с. В UI — «Нет связи с сервером, повторим автоматически» и кнопка «Повторить» |
| Истёк upload-токен | Tus-запрос получает 401 | `onAfterResponse` сбрасывает токен. Для `HEAD` tus сразу повторяет запрос (D8), для остальных запросов срабатывает автоповтор менеджера; новый запрос получает новый токен. Токен, истёкший за время офлайна, обрабатывается так же |
| `HEAD` вернул 401 или 5xx | Без защиты tus-js-client **создаёт новую загрузку с нуля** | Защита в `onAfterResponse` (D8) |
| `HEAD` вернул 404 или 410 (сессия удалена или истекла) | Создаётся новая загрузка с нуля | Допустимо; логируем и показываем «загрузка файла начата заново» |
| Повтор после ошибки (`retryUpload`) | Новый `tus.Upload` получает `uploadUrl` из `file.tus.uploadUrl` и делает `HEAD`; отпечаток в `localStorage` не нужен | — |
| Пауза и продолжение | Используется тот же `tus.Upload`: `HEAD` и продолжение | — |
| 4xx, кроме 401, 409, 423 и 429 | Не повторяется, файл получает `error` | Показать ошибку, автоповтор не запускать |
| Перезагрузка или закрытие вкладки | Загрузка прерывается | Предупреждение `beforeunload`; после возвращения — сценарий §5.10 |

Повторяемые ошибки для автоповтора: сетевая ошибка без ответа, ошибка из защиты `HEAD`, 408, 423, 429 и 5xx. В Uppy 6 событие `upload-error` получает ответ сервера `(file, error, response)`, и по `response.status` ошибки можно классифицировать.

### 5.6 Статусы

**Файл** (на клиенте; вычисляется из `uppy.getState().files[id]` и состояния автоповтора):

| Статус | Как определить |
|---|---|
| `queued` | `progress.uploadStarted == null`, ошибки нет |
| `uploading` | `uploadStarted != null`, `!uploadComplete`, ошибки нет |
| `waiting-retry` | есть `error`, ошибка повторяемая, автоповтор назначен |
| `error` | есть `error`, ошибка неповторяемая |
| `uploaded` | `progress.uploadComplete` |

**Пакет** (клиент и сервер):

```text
draft → creating → queued → uploading
                     ▲        │  ⇅ waiting-retry (нет связи — держит очередь)
                     │        ▼
                     │    completing → [сервер] uploaded → processing → done
                     │        │                                  └──→ failed
                     │        ▼
                     └─── failed (ошибка пакета — ждёт решения, очередь идёт; «Повторить» → в конец очереди)
creating / queued / uploading / waiting-retry / failed → canceled
после закрытия вкладки: queued / uploading → interrupted → (выбор файлов, §5.10) → queued
```

- `interrupted` вычисляется: сервер считает пакет незавершённым, а в этой вкладке у него нет живого инстанса Uppy.
- Статус не хранится отдельно, а вычисляется селектором из состояния Uppy, состояния менеджера и ответа сервера.
- Прогресс пакета считается по байтам: Σ `bytesUploaded` / Σ `bytesTotal`. Скорость и оставшееся время — позже (D19).
- В списке загрузок пакет называется по первому файлу: «flight_0412.mp4 и ещё 2». Тип данных в списке не показываем.
- `upload-success` не означает готовность данных. Данные готовы, когда сервер перевёл пакет в `done`.
- Серверную обработку показываем одним статусом «Обработка» — без контуров и pipeline (D16).

### 5.7 Проверка файлов

```ts
const ALLOWED_NAME_PATTERNS = [
  /\.(jpe?g|png|tiff?)$/i, // фото: .jpg, .jpeg, .png, .tif, .tiff
  /\.(mp4|mov|mkv|avi|ts)$/i, // видео
  /\.mbtiles$/i,
  /\.(zip|rar)$/i, // архив; последний том split-zip; том RAR вида name.part1.rar
  /\.z\d{2,}$/i, // тома split-zip: .z01, .z02 …
  /\.r\d{2,}$/i, // тома RAR старого формата: .r00, .r01 … (первый том — .rar)
  /\.zx\d{2,}$/i, // .zx01 — со слов аналитика; формат уточняется (Q14)
];

export const isAllowedFileName = (name: string) =>
  ALLOWED_NAME_PATTERNS.some((pattern) => pattern.test(name));
```

- Uppy `allowedFileTypes` сравнивает либо MIME, либо последнее расширение целиком (`Restricter.ts`), шаблонов не поддерживает. Поэтому проверка своя, в `onBeforeFileAdded`. При переопределении этого колбэка нужно сохранить защиту от дублей.
- MIME не используем: для `.mbtiles`, `.rar` и томов архивов браузер отдаёт пустой или произвольный тип.
- Если в пакете один тип данных (Q6), допустимые расширения можно сузить по выбранному типу: для «фото» — фото и архивы, для «видео» — видео и архивы.
- Многотомные архивы (D13): группируем файлы по базовому имени и проверяем непрерывность нумерации томов. Результат — только предупреждение, окончательная проверка остаётся за сервером. Схемы именования:
  - split-zip: `name.z01` … `name.zNN` и последний том `name.zip`;
  - RAR новый: `name.part1.rar` … `name.partN.rar`, нумерация с 1;
  - RAR старый: первый том `name.rar`, дальше `name.r00`, `name.r01` …;
  - `.zxNN` в проверке не участвует (Q14).
- Тома одного архива попадают в один пакет — это обеспечивает модель D2.
- Все проверки на клиенте нужны только для удобства. Сервер проверяет то же самое и само содержимое.

### 5.8 Форма (react-hook-form)

Код — `components/UploadForm.tsx`.

- В react-hook-form только поля метаданных (`dataType` и атрибуты типа). Файлы живут в черновике Uppy (D10); при отправке форма проверяет, что он не пуст, и показывает ошибку через `setError('root.files')`.
- Списки атрибутов по типам данных фиксированные (ответ бэкенда): описываются конфигом в коде фронта, бэкенд проверяет те же правила. Источник списков — аналитик (Q6); при изменении правим обе стороны. Пока в форме только выбор типа.
- Поля атрибутов рендерятся по выбранному `dataType`; при смене типа значения атрибутов сбрасываются.
- Отказы при добавлении файлов (формат, размер, дубль) `FileDropzone` показывает по событию `restriction-failed` с причиной на русском.
- `onSubmit`: `await manager.startBatch(draft, { dataType, metadata })`. Ошибку `createBatch` показываем в форме (`setError('root.server')`), черновик сохраняем. После успеха родитель закрывает форму или пересоздаёт её через `key` — загрузка продолжается в менеджере.
- Объекты `File` не кладём в состояние RHF, Redux или `localStorage`.

### 5.9 Правила UX

- Кнопки внутри `<form>` — `type="button"`, кроме submit. У `<input type="file">` нет атрибута `name`.
- `useDropzone` и `useFileInput` из `@uppy/react` работают только внутри `<UppyContextProvider uppy={draft}>`.
- Пока открыта форма, на `window` вызываем `preventDefault` для `dragover` и `drop`: иначе файл, брошенный мимо зоны, откроется в браузере и страница уйдёт.
- Предупреждение `beforeunload`, пока есть пакеты в статусах от `creating` до `completing`, включая `queued`.
- Выход из системы при активных загрузках (Q11): подтверждение «Идут загрузки, они будут прерваны». После подтверждения не вызывать `cancelAll()` и `destroy()` — они удалят загрузки на сервере; пакеты остаются прерванными, и их можно продолжить после входа (§5.10).
- Состояние «нет связи с сервером, повторим автоматически» показываем отдельно от ошибки: это ожидание, а не сбой.
- Доступность: выбор файлов с клавиатуры, видимый фокус, `aria-live` для смены статуса, подписанный progress bar.

### 5.10 Продолжение после закрытия вкладки (Q10)

Автоматически продолжить нельзя: после закрытия вкладки страница теряет доступ к файлам, а открыть файл с диска без действия пользователя браузер не позволяет. Продолжение возможно, если пользователь один раз заново выберет те же файлы. Это то же действие, что и «загрузить заново», только загрузка идёт с места остановки.

1. Во время загрузки менеджер сохраняет в `localStorage` по каждому пакету `batchId` и для каждого файла: имя, размер, `lastModified`, `fileIndex`, `file.tus.uploadUrl` (обновляется по ходу загрузки). Токены туда не пишутся.
2. При следующем открытии приложения менеджер запрашивает `listBatches()` и показывает незавершённые пакеты: «Загрузка прервана на N%», кнопки «Продолжить» и «Отменить».
3. «Продолжить» открывает выбор файлов. Выбранные файлы сопоставляются по имени, размеру и `lastModified`; каждому найденному проставляется адрес загрузки: `uppy.setFileState(id, { tus: { uploadUrl } })`. Плагин подмешивает `file.tus` в опции загрузки (проверено в исходниках).
4. Пакет снова встаёт в очередь. При старте менеджер перевыпускает upload-токен, tus-js-client делает `HEAD` и продолжает с серверного смещения. На 404 или 410 (сервер уже удалил загрузку) файл загружается заново.
5. Если в `localStorage` нет данных о пакете (другой браузер, очищено хранилище), сопоставление идёт по манифесту с сервера, а файлы загружаются с нуля.

Без повторного выбора файлов можно обойтись только в Chromium-браузерах (File System Access API: дескрипторы файлов сохраняются в IndexedDB, после перезагрузки доступ подтверждается одним кликом). Firefox и Safari его не поддерживают, поэтому как основной вариант он не подходит; возможное улучшение после MVP.

## 6. Что фронтенд ожидает от бэкенда и инфраструктуры

Это не задачи фронтенда: раздел нужно передать бэкенду и тем, кто настраивает nginx. Но если эти пункты не выполнены, проявится это как «фронт не докачивает», поэтому их стоит проверить на совместном тесте (этап 1).

### 6.1 Tus-сервер и API

- Поддержка протокола Tus 1.0 с расширениями `creation` и `termination` (нужен для отмены); желательно `expiration`.
- Данные и смещения переживают рестарт сервера. При нескольких инстансах — общий диск и блокировки загрузок.
- Хук на создание загрузки: проверить `batchId`, `fileIndex` и `Upload-Length` по манифесту. Хук на завершение: отметить файл пакета как загруженный.
- Правильный `Location` за прокси (для tusd — флаг `-behind-proxy` и заголовки `X-Forwarded-*`).
- **Upload-токен (D14):** действует только для Tus-эндпоинта и только для своего пакета; срок жизни — с запасом на долгую загрузку (часы); выдаётся и перевыпускается через `POST /api/batches/{batchId}/upload-token` по обычному access-токену; отзывается после `complete` и отмены пакета.
- Коды ответов: на просроченный upload-токен — 401 (не 403); на `HEAD` — 404 или 410, только если загрузки действительно нет (иначе файл загрузится заново с нуля); для постоянных ошибок API — 4xx, но не 409 и не 423 (их фронтенд повторяет). `DELETE /api/batches/{batchId}` сам удаляет все файлы пакета: Tus-`DELETE` может не дойти.
- Брошенные пакеты удаляются по TTL, отсчитанному от последней активности: пакет может часами ждать в очереди (D15) или в статусе «прерван» (§5.10).
- `GET /api/batches` возвращает и незавершённые пакеты пользователя — для экрана «есть незавершённая загрузка».
- Статусы и ошибки пакета не упоминают контуры и pipeline (D16).

### 6.2 nginx

Бэкенд добавит отключение буферизации. Пример для location Tus-эндпоинта, сверить с выбранным Tus-сервером:

```nginx
location /api/uploads/ {
    proxy_pass http://tus_backend;
    proxy_request_buffering off;   # иначе nginx копит тело PATCH и при обрыве Tus-сервер не получит ничего
    proxy_buffering off;
    client_max_body_size 0;        # без ограничения: chunkSize не задаём, файл идёт одним PATCH (D6)
    proxy_http_version 1.1;
    client_body_timeout 300s;
    proxy_send_timeout 300s;
    proxy_read_timeout 300s;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Host $host:$server_port;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

CORS не нужен: Tus и API работают через nginx на том же origin, что и веб-приложение.

## 7. План работ

**Этап 0. Вопросы.** Закрыть открытые вопросы (§3). Начало работы над ядром они не блокируют.

**Этап 1. Серверная часть (делают бэкенд и инфраструктура).** Фронтенду нужен результат: рабочий Tus-эндпоинт за nginx. Пока его нет, ядро фронтенда можно разрабатывать против локального tusd (Docker-образ `tusproject/tusd`). Проверить вместе с бэкендом:
- Tus-сервер за реальным nginx, а не напрямую.
- Файл 5–25 ГБ, обрыв на 40–60%: по логам сервера продолжение идёт с сохранённого смещения.
- Рестарт Tus-сервера во время загрузки.
- Убедиться, что nginx не буферизует запросы: смещение на сервере растёт по ходу `PATCH`.

**Результат:** подтверждённое сервером смещение сохраняется, уже переданные гигабайты заново не отправляются.

**Этап 2. Ядро фронтенда.** Каркас готов: `src/upload/`. Предыдущая, более объёмная версия была проверена интеграционным тестом против `@tus/server` за прокси, имитирующим nginx: очередь из двух пакетов, сбой с ответами 502 посреди загрузки, отзыв токенов сервером (401), отмена активного пакета, короткий сбой 150 мс. Ни один файл не перезапускался с нуля; без защиты `HEAD` короткий сбой перезапускает файл (3 из 3 прогонов). После упрощения каркаса тест нужно обновить под новый API и прогнать заново. Для ручной проверки есть заглушка бэкенда и страница (`npm run mock`, `npm run dev`; см. CLAUDE.md). 13.10.2026 в Chrome проверено: файл 30 МБ, заглушка остановлена на середине и запущена через 12 с; после повтора загрузка продолжилась с серверного смещения (около 15 МБ), а не с нуля, файл на сервере совпал с исходным. Дальше — прогнать сценарии §8.

| Многотомный архив с пропущенным томом | Предупреждение, отправить можно (D13); сервер сообщает ошибку в статусе пакета |
| Сеть отключена на 30 с и на 10 мин | После включения загрузка продолжается с серверного смещения без действий пользователя |
| Tus-сервер остановлен на 5 мин (nginx отвечает 502) | Статус «нет связи, повтор»; после запуска сервера — продолжение со смещения, не с нуля |
| Рестарт nginx во время `PATCH` | То же |
| Upload-токен истёк во время загрузки и во время долгого офлайна | Токен перевыпускается, загрузка продолжается без перезапуска с нуля |
| Сессия пользователя закончилась во время загрузки | Загрузка продолжается на upload-токене; если нужен перевыпуск — повторы, пока пользователь не войдёт снова |
| Модалка закрыта во время загрузки | Загрузка продолжается, статус виден в списке пакетов |
| Второй пакет отправлен, пока идёт первый | Второй в статусе `queued`, стартует после завершения передачи первого |
| У первого пакета постоянная ошибка (например, 403), в очереди второй | Первый — «ошибка», второй стартует, когда у первого не осталось загружающихся файлов. «Повторить» ставит первый в конец очереди и не запускает его параллельно |
| У первого пакета нет связи, в очереди второй | Второй ждёт; первый продолжает сам, когда связь вернётся |
| «Повторить» у пакета, который ждёт в очереди | Ничего не происходит: пакет стартует в свою очередь |
| Отмена пакета | Запросы остановлены, `DELETE` отправлен, на сервере пакет `canceled`; следующий в очереди стартует |
| Перезагрузка страницы во время загрузки | Предупреждение `beforeunload`; после перезагрузки — «Загрузка прервана на N%»; выбраны те же файлы → продолжение с места остановки; выбран изменённый файл → этот файл загружается заново |
| Обрыв на 99% | Нет дубля файла; `complete` идемпотентен |
| 1000+ фото в пакете | UI не тормозит, лимит параллельности соблюдается |
| Файлы больше 4 ГБ и около 25 ГБ | Правильные размеры и прогресс |
| Статусы и ошибки пакета | Нигде не упоминаются контуры и pipeline |
| Две вкладки | Независимые пакеты без конфликтов |

## 9. Критерии готовности

- [ ] Закрытие модалки или таба не прерывает загрузку.
- [ ] После восстановления сети и после восстановления сервера загрузка продолжается с серверного смещения без действий пользователя.
- [ ] Ни один сценарий из §8 не приводит к повторной передаче файла с нуля (кроме истёкшей серверной сессии и изменённого файла).
- [ ] Многочасовая загрузка не прерывается из-за истечения токенов.
- [ ] Пакеты, отправленные во время загрузки, ждут в очереди и запускаются по порядку.
- [ ] После закрытия вкладки пользователь видит прерванную загрузку и может продолжить её, выбрав те же файлы.
- [ ] Метаданные проверяются до начала передачи; файлы чужого пакета или не из манифеста сервер не принимает.
- [ ] Пользователь видит статус передачи и обработки по каждому пакету, без упоминания контуров.
- [ ] Отмена пакета очищает данные на сервере.
- [ ] Большие файлы не читаются целиком в память; объекты `File` не попадают в состояние формы.
- [ ] Интерфейс соответствует дизайн-системе и доступен с клавиатуры.
- [ ] Сценарии из §8 пройдены.

## 10. Типичные ошибки

1. `useEffect(() => () => uppy.destroy(), [uppy])` в компоненте формы: закрытие модалки удаляет загрузки на сервере.
2. Считать `retryDelays` «возобновлением после восстановления связи»: при недоступном сервере и онлайн-браузере попытки заканчиваются за секунды.
3. Не защитить `HEAD`: при 401 или 5xx загрузка тихо начинается с нуля.
4. Взять upload-токен один раз и не перевыпускать его при 401, или замкнуть в колбэках Tus устаревшие функции из props.
5. Оставить буферизацию запросов или ограничение размера тела в nginx: после обрыва загрузка начнётся с нуля или получит 413.
6. Проверять тип файла по MIME.
7. Один инстанс Uppy на всё приложение с общими meta: метаданные разных пакетов перемешаются.
8. Хранить `File` в состоянии RHF, Redux или `localStorage`; хранить токены в `localStorage`.
9. Считать `upload-success` готовностью данных.
10. Подключить `@uppy/tus` к обычному `multipart/form-data` endpoint.
11. Полагаться на API Uppy «по памяти»: между 5.x и 6.x изменились импорты. Сверять с исходниками установленной версии.
